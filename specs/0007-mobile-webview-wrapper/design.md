# Design — Mobile WebView Wrapper

- **Status:** Draft
- **Spec ID:** 0007
- **Implements:** requirements.md

## 1. Overview

A new Flutter project (location TBD — see requirements.md's open questions) contains a
single-screen app: a full-screen `WebViewWidget` (via the `webview_flutter` package)
that loads a build-time-configured base URL. A thin controller layer handles back-button
interception, loading/error UI, and redirecting off-origin navigation to the system
browser. No native Android/iOS code is hand-written — Flutter's plugin abstracts the
platform WebView (`android.webkit.WebView` / `WKWebView`) behind one Dart API.

## 2. Architecture

```
mobile/                              (new Flutter project; see open question on location)
├── lib/
│   ├── main.dart                    → runApp(), reads compile-time BASE_URL
│   └── webview_screen.dart          → WebViewWidget + PopScope (R3) + loading/error UI (R4)
│                                       + NavigationDelegate host-check (R5)
├── android/                         → generated by `flutter create`, icon/splash only (R6)
├── ios/                             → generated by `flutter create`, icon/splash only (R6)
└── pubspec.yaml                     → webview_flutter, url_launcher

Build-time config: --dart-define=APP_BASE_URL=https://app.example.com
  read via String.fromEnvironment('APP_BASE_URL') in main.dart (R1.2)
```

Request flow: the WebView issues normal browser-equivalent HTTP requests straight to
the deployed Next.js app's existing routes — there is no proxy, no bridge, and nothing
in `src/**` is aware it's being loaded from inside a WebView instead of a real browser.
Sign-in (`src/app/[locale]/sign-in`) sets Better Auth's session cookie exactly as it
would for desktop Chrome; the platform WebView's cookie store persists it (R2).

## 6. Security & multi-tenancy

- No new attack surface on the backend: the WebView is an HTTP client hitting the
  app's already-public URL, subject to the same auth/tenant scoping
  (`src/lib/crud.ts`, `getSession`) as any other client. Multi-tenancy is unaffected —
  see CLAUDE.md's Architecture section on `organizationId` scoping, which this spec
  does not touch.
- `NavigationDelegate.onNavigationRequest` allow-lists the configured base URL's host;
  any other host is handed to `url_launcher` and the in-app navigation is cancelled
  (R5.1) — this keeps the WebView from becoming an open-ended embedded browser for
  arbitrary sites.
- The WebView must **not** enable arbitrary local file access or JavaScript bridges
  beyond what `webview_flutter` exposes by default — no `addJavascriptInterface`-style
  bridge is introduced by this spec (none of the requirements need one).
- Session cookie handling is entirely delegated to the platform WebView's native
  cookie store (`CookieManager` / `WKWebsiteDataStore`) — no cookie value is read,
  copied, or stored by app code, so there's no new place for a session token to leak.

## 7. Testing strategy

Playwright (this repo's existing E2E tool) does not exercise a native mobile
WebView shell, so this spec's acceptance criteria are verified differently than the
rest of the repo:

- R1 (loads base URL), R4 (loading/error state): manual verification — run
  `flutter run` against a local dev server (R1) and against a deliberately stopped
  server / airplane mode (R4), on both an Android emulator and an iOS simulator.
- R2 (session persists): manual verification — sign in inside the running app, force-
  close it, relaunch, confirm still signed in.
- R3 (back button): manual verification on Android only (no hardware back button on
  iOS) — navigate a few pages deep, confirm back button steps back before exiting.
- R5 (external links leave the app): manual verification — tap a link to a
  non-base-URL host, confirm it opens the system browser and the app's WebView is
  unaffected.
- R6 (branding): visual check of the installed app's icon and splash screen on both
  platforms.
- Flutter's own `flutter test` widget-test harness can cover the pure-Dart logic
  (host-allow-list check, back-button-history check) in isolation without a real
  device, and should be added for those two branches specifically since they're the
  parts most likely to regress silently.

## 8. Risks & alternatives considered

- **Alternative: Progressive Web App (add-to-home-screen)** — zero new codebase, no
  app store review risk, works today with no build step. Rejected as the primary
  approach only because the ask was specifically for installable Android/iOS apps
  (store presence, app icon in the OS app drawer) — worth revisiting if store
  distribution turns out not to matter (see requirements.md's open question on this).
- **Alternative: Capacitor (Ionic)** — same WebView-wrapper concept, but configured in
  JS/TS/JSON instead of Dart, which would avoid introducing a second language into a
  TypeScript-only repo. Rejected in favor of Flutter only because the user specifically
  asked about a Flutter wrapper; if minimizing new-language surface matters more than
  matching the ask, Capacitor is a closer alternative than it might first appear and
  worth reconsidering.
- **Risk: Apple App Store 4.2 rejection** (see requirements.md's Constraints) — a
  WebView-only app with no native-feeling functionality is a known rejection pattern.
  _Mitigation:_ none engineered here; flagged as a distribution-stage risk to accept
  or address (e.g. adding a couple of genuinely native touches) before submitting.
- **Risk: cookie store behavior differs slightly by platform/WebView version** —
  Android's `CookieManager` and iOS's `WKWebsiteDataStore` are both persistent by
  default in `webview_flutter`, but this hasn't been verified against this project's
  exact Better Auth cookie flags (`SameSite`, `Secure`). _Mitigation:_ the manual R2
  verification step above is the actual proof; if it fails, the fix is almost
  certainly a `webview_flutter` configuration flag, not a change to `src/lib/auth.ts`.
